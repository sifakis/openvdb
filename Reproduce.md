## City flood scene

A basin of water in the river (585,000 m^3, 10 m above street level) bursts through three openings of a flood wall
and floods a city of 1.9 km x 1.8 km for 80 simulated seconds. The water is a narrow-band level set on a NanoVDB
`ValueOnIndex` grid, tracked by `LevelSetTracker` (`track()`) with `PropagateSign`; the city is a signed distance field
made by `MeshToSDF`.

| | |
|---|---|
| Code | `nanovdb/nanovdb/examples/ex_fluid_city_flood_cuda/` (its `README.md` describes the scene, the files and the method's limits) |
| Result | `output/flood/movie/movie.mp4`: 641 frames, 2560 x 1440, 24 frames per second, 26.7 s (8 frames per simulated second, so three times real time) |
| Simulation | NVIDIA GeForce RTX 5090 (32 GB): 3 h 8 min |
| Rendering | NVIDIA RTX PRO 3000 Blackwell laptop GPU (12 GB): about 27 s per frame, 4.8 h |

### Assets to download

| Asset | Size | Link |
|---|---|---|
| NVIDIA Omniverse "AEC City Demo Pack" (`AECO_CityDemoPack_NVD`, version 10011) | 197 MB | https://d4i3qtqj3r0z5.cloudfront.net/AECO_CityDemoPack_NVD%4010011.zip, listed on https://docs.omniverse.nvidia.com/usd/latest/usd_content_samples/downloadable_packs.html |

`get_assets.sh` downloads and unpacks it into `assets/` and exports the city's triangles (`output/city.obj`, 15 MB,

### Steps

All commands run in `nanovdb/nanovdb/examples/ex_fluid_city_flood_cuda/`.

```
CCCL=<cccl checkout> OPENVDB_ROOT=<OpenVDB installation> ./build.sh
export RENDER_PYTHON=<python with the packages above>
./get_assets.sh                    # city pack -> assets/, output/city.obj
./run_city.sh                      # solids, MeshToSDF, 80 s of flood -> output/flood/
./render_movie.sh                  # water meshes, 641 images, output/flood/movie/movie.mp4
$RENDER_PYTHON -I tools/check_run.py output/flood 128 288 400 520 640
```

The binary of the paper's run was built natively for the RTX 5090, with three definitions that keep nvcc from parsing
the host compiler's AMX headers:

```
CUDA_ARCH_FLAGS="-arch=sm_120" \
EXTRA_FLAGS="-Xcompiler=-D_AMXTILEINTRIN_H_INCLUDED -Xcompiler=-D_AMXINT8INTRIN_H_INCLUDED -Xcompiler=-D_AMXBF16INTRIN_H_INCLUDED" \
CCCL=<cccl checkout> ./build.sh
```

`build.sh`'s default instead emits PTX that the driver compiles for the GPU at hand; that default is what was built and
run on the laptop.

On a GPU with 12 GB, the same scene at 0.5 m voxels: `./run_city.sh probe 0.5 80` and `./render_movie.sh probe`.

### How closely a reproduction matches

- **Scene and MeshToSDF are deterministic.** `build.txt` and the mesh are the same byte for byte, and the signed
  distance field has the same values.
- **The solver is not.** Two runs of the same binary on the same GPU agree to all printed digits for the first reports
  and then drift apart in the last digits: at 0.5 m voxels the volumes of two runs differed by at most 113 of 4.39
  million cells (0.003%) over 5 seconds, with the same number of steps at every report. Over the full run expect the
  numbers above to a few digits and the same look, not the same bits.
- **The renderer** gives the same image up to noise: a frame rendered twice from the same mesh differed by 0.11 of 255
  per channel on average and by at most 10.

### How this branch's copy was checked

The paper's run was made with development copies of these files, built against the same `LevelSetTracker` headers
and against the MeshToSDF version that preceded this branch's, with this branch's `nanovdb/math/Proximity.h`. The
full 0.25 m run was not repeated from this branch. What was checked, on the laptop GPU:

- `get_assets.sh`: `output/city.obj` is identical to the one the paper's scene was built from.
- `build_city.py` at 0.25 m: `build.txt` and the mesh are identical to those of the paper's run.
- `gen_sdf` at 0.5 m: all 186,864,013 values identical to the development version's; the grid buffers differ in the
  two bytes of the NanoVDB version number.
- `eulerian` at 0.5 m, 5 seconds: against the development binary the volume differs by at most 81 cells, within the
  113 cells between two runs of the development binary itself.
- `run_city.sh`'s restart: the solver was stopped after the first state file and continued from it to the end.
- `mesh_band` and `render_city.py` on frames 320 and 321 of the paper's run: the meshes are identical to the ones the
  movie was rendered from, the images equal the movie's up to the noise given above.

### Notes

- An earlier attempt of the same run on the RTX 5090 stopped at 35.5 simulated seconds with CUDA error 702 ("the launch
  timed out and was terminated"); the cause was not found. That is why `run_city.sh` writes state files and continues
  from the newest one. The paper's run finished in a single attempt.
- A state file holds the water, its velocity and the grids, but not the drops in the air or the marker particles: a
  run that continued from one has almost no drops in the first frame after it.

## Constructive solid geometry

Union, intersection, difference and complement of narrow-band level sets on NanoVDB `ValueOnIndex` grids
(`csgUnion`, `csgIntersection`, `csgDifference`, `csgComplement`). The result's band is built from the retained
voxels of the inputs, and its invert masks from the inside and outside states of the inputs at the leaf, lower and
upper levels, without a sign propagation pass.

| | |
|---|---|
| Code | `nanovdb/nanovdb/tools/cuda/CSG.cuh`; the design is in `nanovdb/nanovdb/examples/ex_csg_nanovdb_cuda/CSG-design.md` |
| Programs | `nanovdb/nanovdb/examples/ex_csg_nanovdb_cuda/` (its `README.md` describes each program and what the tests check) |
| Figure data | `csg_viewer_slices` and `csg_viewer_voxels` of that example; `viewer/README.md` there describes the files |
| Comparison with OpenVDB | `nanovdb/nanovdb/examples/ex_csg_nanovdb_cuda/openvdb_comparison/` (its `README.md` has the method, the full tables and the limits; `results/` the output of the runs quoted here) |
| Hardware of the numbers below | NVIDIA RTX PRO 3000 Blackwell laptop GPU (12 GB), Intel Core Ultra 7 265H (16 threads) |

### How closely a reproduction matches

- **The results of the operations are deterministic.** The tests compare values exactly, and the comparison with
  OpenVDB is exact in every voxel.
- **The times are not.** They need an idle GPU, mains power and the `performance` power profile on the laptop.
  OpenVDB's in-place times vary most: across three runs the in-place union at 2048 had medians between 4.5 and
  5.4 ms.

## Hydra

A modeling example for the CSG operations: nine triangle meshes of snakes become one hydra with nine heads. One
mesh is the body and keeps its own head; each of the other eight gives its head.

```
hydra = body | (model_1 & cutter_1) | (model_2 & cutter_2) | ... | (model_8 & cutter_8)
```

`|` is `csgUnion` and `&` is `csgIntersection`; every operand is a narrow-band level set made by `MeshToSDF`: 17
conversions, eight intersections, eight unions.

| | |
|---|---|
| Code | `nanovdb/nanovdb/examples/ex_csg_nanovdb_cuda/hydra/` (its `README.md` describes the operands, how the heads are placed, the files and the limits) |
| Result | `output/1024/hydra.band` (the level set), `hydra.meshbin` (its surface as triangles), `hydra.png` (path-traced image, 1920 x 1080) |
| Animation | `Supplementary material/video/Applications/hydra.mp4` of the paper's repository (1036 frames, 1920 x 1080, 24 frames per second, 43.2 s), made by `figure factory/CSG/hydra/make_animation.py` of the paper's repository from the programs of this example; the `README.md` there describes it |
| Hardware of everything below | NVIDIA RTX PRO 3000 Blackwell laptop GPU (12 GB), Intel Core Ultra 7 265H (16 threads) |

### Meshes

The nine meshes were generated with Meshy AI (www.meshy.ai). They are not in this repository; contact the authors
for them. The example's `README.md` lists their file names, vertex and triangle counts and SHA-256 sums; together they
have 23,344,018 triangles and take 1.7 GB.

The lengths of the necks, the places of the cuts and the angles in `plan_hydra.py` were chosen by hand for these
nine files. With other meshes the programs run, but these numbers need to be chosen again, and the numbers below
do not apply.

### How closely a reproduction matches

- **The level sets are deterministic for the same plan.** Two runs at 220 voxels wrote the same `body.band`,
  `head_7.band` and `hydra.band`, byte for byte.
- **The plan was made once.** Whether another machine, or other versions of numpy and scipy, give the same plan to
  the last digit was not tested; a plan that differs moves a head slightly and changes the counts above.
- **The pictures are path traced** and differ in noise from run to run.

## Mean curvature flow

The Stanford dragon's level set moves by mean curvature with its volume preserved: the scales, the horns and the
legs go first, the loop of the tail closes, and the body ends as a sphere of the dragon's volume. Every step is a
curvature update on the GPU followed by `LevelSetTracker::track()`; the level set is made by `MeshToSDF`.

| | |
|---|---|
| Code | `nanovdb/nanovdb/examples/ex_mean_curvature_flow_cuda/` (its `README.md` describes the method, the files, the checks and the method's limits) |
